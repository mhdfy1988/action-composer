## 二、P0：先定基线，不从大重构开始

### 工作内容

1. 核对 `reference-compare-demo` 的图像加载、帧顺序、播放、参考线、整组校准和腰点补偿，实现与测试逐项列出。
2. 选择性迁入可复用代码并保留来源记录；不复制依赖目录、缓存、日志和私人素材，不动旧服务。
3. 约定素材、动画片段、舞台、图层、变换、时间和工程版本的最小数据结构。
4. 先定义无界面依赖的领域接口，再确定基础前端、测试、PNG 编解码与打包方案。通用能力先评估成熟库，记录解决问题、依赖成本和替代范围。
5. 确定独立开发端口、演示素材与简洁界面；不使用虚构可操作入口。

### 核心约定

- 原始图像不可变，编辑操作保存为参数和草稿，结果另存。
- 帧身份、原始尺寸、帧顺序、帧持续时间与画布偏移必须保留；不得用文件名排序猜测已有清单顺序。
- 时间使用明确精度的整数单位或有理数，不累加浮点时间作为真值；固定帧率是简化输入，不排除逐帧时长。
- 舞台采用项目自己的像素坐标、统一原点和单位；屏幕缩放不改变数据。引擎坐标与单位由适配器转换。
- 裁剪后保留原尺寸、裁剪矩形和原点关系，禁止逐帧紧裁后丢偏移造成角色跳动。
- 多动作组分别校准；动作组和舞台图层不是同一对象。

### 验收

小型合成夹具能表达两个不同时长的帧、透明边距、不同尺寸、两组动作和独立变换；协议有运行时校验与错误反馈。复用清单区分已迁入、未迁入、需改造，不把旧项目测试直接算作新项目证据。

## 三、P1：先交付能保存和输出的帧校准

### 工作内容

- 单张 PNG、多张帧和已支持格式的帧清单从同一个入口导入为普通动作；用作参照的单图也不设独立类型。不默认支持任意视频、ZIP 或第三方格式。
- 导入无清单时允许确认顺序与帧率，不静默猜时序。
- 连续灰色工作台内勾选显示多个普通动作，无固定输出范围或特殊基准图；支持原点参考线、播放、暂停和逐帧查看；图片点击选中后编辑，空白拖动只平移观察视图。
- 多动作组各自保留缩放和水平／纵向偏移，支持锁定某轴；保留已验证的人工腰点水平补偿，但不将它称为自动识别。
- 提供撤销、恢复、重置与关闭保护。参数变化、原点、参考线和动作选择的职责分开。
- 工程保存与重开携带必要素材或可校验引用；首版优先自包含工程包，不能依赖旧工具目录或浏览器缓存才能恢复。
- 校准结果先测量本组所有帧的可见内容，取共同范围加留白，再生成统一尺寸、原点的透明 PNG 序列与清单；保留帧间位置，不逐帧独立裁切或缩放。其他动作与观察视图不参与输出计算。

### 验收

用户素材从导入、校准、保存、重开到导出完整跑通；重开后帧顺序、尺寸、时间、原点和变换一致。下载后回读文件，检查真实 RGBA、透明区域、帧数量和偏移，不只检查下载按钮。失败或取消保留此前工程，晚到请求不能替换新素材。

## 四、P2：无模型自动对齐＋人工兜底

当前增量：“首帧对齐”按钮以当前动作为固定基准，批量匹配其余全部动作；“位移”提供当前组纵向补偿与逐帧人工修正。两者独立、可撤销；均不是身体识别，姿态变化需检查。自动横向补偿仍未实现。具体边界见 README，以下为继续增强方向。

### 工作内容

- 先区分整组尺寸校准、整体定位、逐帧位移补偿三个问题，不把它们合成一个不透明算法。
- 算法选型先查成熟实现，并用待机、跑步、跳跃、攻击、武器伸出、尾巴摆动等样例比较。
- 使用透明度轮廓、用户基准与可选标点等非模型信息；不得把每帧包围框中心或高度直接当作身体位置和身高。
- 自动对齐由位置与缩放策略组成，允许分别启用；首版整组统一缩放，不默认逐帧拉伸。
- 明确保留／消除水平运动及纵向运动的选择。跳跃不应因对齐而默认贴地。
- 一键匹配完成直接应用并可一步撤销，计算可取消；显示无法可靠估计的原因，人工修正复用既有编辑能力，不隐藏失败。

### 验收

用合成已知变换测量数值误差，再用真实动作人工检查自然度。尾巴、刀光或动作幅度变化不能自动触发角色缩放；无有效主体、遮挡严重等情况明确报错或要求标点，不宣称所有角色均能自动识别。

## 五、P3：把校准舞台扩展为分层舞台

### 工作内容

- 同一舞台添加角色、武器、特效等图层，图层引用图片或动画片段。
- 支持独立位置、旋转、等比缩放、可见性、锁定和遮挡顺序；首版只做明确的混合方式，不承诺引擎无法一致复现的效果。
- 一个统一时钟驱动全部图层，不使用互相漂移的独立计时器。
- 校准用于修正素材基础关系，舞台变换用于摆放图层，两者分开记录，避免重复叠加。
- 首版武器可以手动定位；自动握持跟随、人体识别、骨骼解算不在范围内。

### 验收

角色＋武器＋至少两层特效组合播放；切帧、暂停和拖播放头得到同一画面。隐藏／锁定／重排图层不修改原素材，复制实例不串改原实例参数，工程重开恢复全部图层。

## 六、P4：时间轴与可控跟随

### 工作内容

- 图层轨道上放置动画片段，支持起播、持续时间、循环、源范围和播放速率。
- 时间轴缩放只改变显示，片段始终按真实时间比例展示；短片段仍可定位和操作。
- 加入位置、旋转、缩放关键帧，以及离散的可见性／遮挡变化；插值规则明确。
- 武器跟随先用人工挂点或关键帧，不根据画面自动猜测。挂点属于素材坐标，通过变换进入舞台坐标。
- 截断、延长、循环和最后一帧保持分别定义，不能在片段结束后无意残留特效。

### 验收

完成“角色挥剑→武器跟随→刀光出现→特效结束”的小例子。随机跳转与从头播放在同一时刻输出一致；帧边界、循环边界、关键帧、撤销和工程恢复均有测试。命中伤害等游戏规则不由播放器自动执行。

## 七、P5：三种输出与预览一致

### 输出内容

1. 校准素材包：独立动作帧、时间、尺寸、原点与裁剪偏移。
2. 合成序列帧／图集：按选定输出帧率采样统一舞台，明确画布、采样边界、透明度、图集间距及页尺寸上限。
3. 分层编排包：独立素材与版本化清单，保存图层、片段、时间、变换及支持的插值和混合语义；工程草稿字段与游戏运行数据分开。

### 验收

舞台预览和导出调用同一时间求值与变换逻辑，不能另写一套近似渲染。对固定时刻比较像素与定位；核对透明边缘、裁剪恢复、末帧、图集映射、多页和文件预算。导出失败不给半成品成功提示；不支持的效果必须拒绝或明确要求烘焙，不能静默丢失。

## 八、P6：引擎适配，不承诺一个 JSON 通吃

建议先验证 Three.js，再选一个实际游戏引擎完成闭环；Godot、Unity、Cocos 的具体优先级根据用户项目决定，不并行承诺全部完成。

- Three.js：最小分层播放器，验证纹理、帧切换、统一时钟和空间变换。
- Godot：验证帧动画资源和分层场景／播放器的导入路径。
- Unity：验证精灵切片、原点、单位与动画或播放器的导入路径。
- Cocos：固定 Creator 版本后验证帧资源与编排播放，不混用不同大版本接口。

各适配器分别查询官方文档和已有能力，固定版本、输出示例并在实际引擎运行。测试角色落点、动作切换、换武器、特效同步、透明边缘和层级，不能用网页预览代替引擎验收。未接通平台明确标记未支持。

## 九、代码结构原则

先按职责划分，按功能需要逐步建目录，不提前生成大量空模块：

- 领域核心：素材描述、时间求值、坐标变换、校准和编排；不依赖 DOM、Cordis 或引擎 API。
- 应用流程：导入、编辑会话、撤销历史、保存和导出用例。
- 界面：舞台、素材列表、属性面板、时间轴；只发出编辑意图，不复制领域计算。
- 基础设施：文件、图片解码、持久化、打包和后台任务。
- 适配器：引擎导出／播放，以及未来动作工坊插件入口。

技术栈优先延续原生前端的小规模结构；是否引入类型系统、构建库和组件方案在 P0 根据实际成本决定，不为架构名词增加框架。通用依赖经适配层隔离，来源和许可留档。
